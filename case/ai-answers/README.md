# AI 的实际回答

书里两处说「我把这段丢给 AI」。这个目录是那些回答的**原件**，不是转述。

## 为什么要有这个目录

第 06、07 章都建立在一个判断上：**AI 给出的抽象，往往比需求多。** 这句话如果只是作者的观察，读者只能选择信或不信。

放上原件，读者可以自己数。

## 两次实验

| | `branch-refactor/` | `editor-refactor/` |
|---|---|---|
| 对应章节 | 06 | 07 |
| 输入 | `v0.4/src/render/branches.ts`，六个 `if` | 十二个位置参数的调用 |
| 请求 | 「分支太多了，帮我整理一下」 | 「参数太多了，帮我整理一下，以后好扩展」 |
| 产出 | **4 个文件，169 行** | **9 个文件，1186 行** |
| 核心方案 | 表驱动（和书里的结论一致） | 分组 options（和书里的结论一致） |

## 结果出乎预料

**两次它都给对了方向。**

第 06 章原本写的是「它会给你策略模式（七个文件）」，第 07 章写的是「它会给你建造者模式」。**做完实验，两条都不成立**，两章都按真实结果重写了。

真实的情况是：**方向对，规模不对。**

- 六条规则的整理，核心大概三十行，它给了四个文件 169 行（多出来的是一个 2594 组输入的对拍脚本和一个入口文件）
- 十二个参数的分组，方向无误，但它一路做到了九个文件 1186 行

**这两者都不算错。** 它多做的每件事都能说清理由。问题在于它替你做了主张——主张这个渲染器值得一个对拍脚本、主张主题应该变成可注册资源。

**你的项目是不是这样，只有你知道。**

## 怎么做这两次实验的

每次都是独立会话，只给代码和那句话，不给任何关于这本书的上下文。要求里明确写了「不要揣测这次任务有什么别的意图，也不要刻意选择某种风格」。

同一个请求你去做，大概会得到类似但不完全一样的东西——**这正是这些答案的性质：它们是分布的样本，不是唯一的正确答案。**


## 一处后来被推翻的说法

`branch-refactor/NOTES.md` 里有这么一句：

> 这里顺序确实影响输出（含反引号的加粗文本，必须先认出代码再包 `<b>`）

**这句话是错的。** 后来我把六条规则做了全排列（720 种），拿正常文本（包括 `**\`code\`**`）跑，输出完全一致——六条规则匹配的标记互不重叠。

顺序确实有影响，但只在标记交错的畸形输入上：`[**~~](](~~**)` 这种半截标记，不同顺序能给出四种结果。

第 06 章按实测重写了这一段。**NOTES.md 保持原样**，因为它是那次实验的原件——它错了，本身就是「AI 的回答需要核实」的一个例子。


## 第 07 章那道题的答案之一

`editor-refactor/src/renderer.ts` 里有一个**死分支**：

```ts
readonly #syntaxElements = new Map<SyntaxFeature, HTMLElement>()   // 声明

applySyntax(feature, enabled) {
  this.#container.dataset[...] = enabled ? 'on' : 'off'
  const element = this.#syntaxElements.get(feature)                 // 读
  if (element !== undefined) element.hidden = !enabled              // 永不执行
}

destroy() { this.#syntaxElements.clear() }                          // 清
```

**这个 Map 从来没有被 `set` 过。** `get` 永远返回 `undefined`，那个 `if` 是一个永远不会进去的分支，`clear()` 清的是一个空 Map。

第 07 章请读者对着那 1186 行挑「哪几行今天用得上」，这就是答案之一。

**没有删掉它**——这份文件是那次实验的原件，改了就不是 AI 当时给的东西了。
