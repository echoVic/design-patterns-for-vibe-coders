# 这本书是怎么做出来的

写给接手的人（也可能是三个月后的我自己）。重点不是过程，是**哪些地方曾经出错、怎么发现的**。

## 顺序：先写案例，再写章节

第 00 章和第 04 章是唯一两章「从代码里长出来」的：

- 写 `v0.2` 的时候，注意力全在分层上，**把 v0.1 的 HTML 转义弄丢了**。逐行对比才发现。这件事成了第 00 章的论点。
- 第 04 章原本写的是「加 IndexedDB 会报错」。真去写了一遍，发现**它不报错，只是静默返回空数组**——比报错更糟。整章按这个结果重写了。

**案例不写出来，书是空的。**

## 三轮独立审读

初稿完成后，请了两个**独立会话**（不给任何关于这本书的上下文）分别审读。

### 第一轮找出 11 个问题，最严重的三个

1. **第 00 章的语言史论断是错的**。原写「设计模式是在 Java 和 C++ 的年代总结出来的」，但 GoF 成书 1994，Java 1995 才发布。这是全书解释「AI 为什么给你 Java 形状」的地基。
2. **第 02 章说「v0.1 没有任何隐藏前提」**——说反了。v0.1 裸调 `JSON.parse`、`setItem` 没包 try，隐藏前提比 v0.2 更多。
3. **第 16 章编造了消费者**（说 `NoteStore` 有「界面、导出、统计」三个消费者），而案例里根本没有导出和统计模块。

还有：第 11 章的 git diff 列了 v0.2 没有的文件；第 13 章的建议与第 10 章立场冲突；附录 A 把正文没讲过的模式列成索引。

### 第二轮找出「同类复发」

改完第一轮的 11 条之后，第二轮又抓到：

1. **第 13 章有一整段被写了两遍**（改的时候插入了新版本，没删旧的），方式二的内容丢了。这是唯一一处硬编辑事故。
2. **「MemoryNoteStore 测试在用」是新的编造**——仓库里根本没有测试。而且它是第 16 章最终判据的唯一证据。
3. **案例文档里还留着「三个消费者」**——第一轮只改了正文，`store.ts` 和两个 README 里的编造还在。

**第二轮的教训比第一轮值钱**：修正了一处编造，会在同类的另一个地方留下同样的编造。查一遍不够，要按「同类」再查一遍。

## 两次真实实验

第 06、07 章原本写「AI 会给策略模式」「AI 会给建造者」。为了不凭印象说话，开了两个独立会话，只给代码和一句请求。

**结果推翻了原来的论断**：两次它都给对了方向（表驱动、分组 options），只是规模大得多（169 行 vs 62 行的核心；1186 行 for 一个十二参数的构造函数）。

两章都按真实结果重写了，论证从「AI 会过度设计」改成「**方向对，规模不对**」。原件在 `case/ai-answers/`。

**这次实验的价值在于它推翻了我自己的论断。** 如果只是引用印象，这两章现在还是错的。

## 第三轮：改出来的新问题

第二轮修完之后又请了一轮，专门查这批改动。结果抓到三件事：

1. **README 里新加了一句「v1.1 能撑……搜索」，但搜索根本没进 v1.1**（那是第 11 章测完就撤掉的改动）。**编造是改出来的，不是写出来的。**
2. **第 13 章的「方式二」和新写的内容自相矛盾**：它示范的 `env.ts` 里 `new LocalNoteStore()`，正是第 10 章反对的写法。改一处的时候没有回头对另一章。
3. **「加一种语法改 2 处」是我没测准**。实测要 3 处：规则表、`RenderOptions` 接口、默认开关。

第 3 条有两个修法：改成 3，或者把 v1.1 改成从规则表推导开关类型。**选了后者**——实验里 AI 给的那版就是这么做的，它比我手写的那个更好。改完 v1.1 从 165 行长到 171 行（后来删掉一个没人读的字段，现在是 169 行），加语法真的只要改一行。

顺带补了 `store.test.ts` 里一条断言：接口的注释写「最近追加的在前」，原来的测试只测了「新加的排最前」，测不出「按 createdAt 排序」这种改法。新断言能测出来（验证过：把它改成按 createdAt 排序，测试会失败）。

**三轮下来的规律：每一轮修完，下一轮总能在「同类的地方」再找到一处。** 第一轮的编造在案例文档里留了副本，第二轮的修正引入了新的编造，第三轮发现改一处没对另一章。**改完要按「同类」再扫一遍，不是看一眼改的那行就完事。**

## 第四轮：一个一直没被发现的 bug

第四轮抓到的问题比前三轮都实在：

**规则表里「引用」那条从来没生效过。** `render` 先转义（`>` → `&gt;`），再套规则，而引用规则的正则要求行首是字面的 `>`。两个版本写的是同一个错。

**而第 06 章的对拍脚本一路绿灯**——因为它比对的是「两份实现是否一致」，不是「结果对不对」。两版错得一样，它就无感。

这件事直接改掉了那一章的结构：加了一节「但『一致』不等于『对』」，并给脚本补了一组期望输出断言。反向验证过：把引用规则改回错的那种写法，脚本会报「期望输出不符」。

**这一轮的另外七处，有四处的性质是「上一轮说修了、其实没修上」：**

- 第 13 章方式二那条：commit message 写了，`git show` 是空的（脚本的 `assert` 没拦住）
- 附录 A 补了名字，但正文还写着「只覆盖了十个」
- 测试行数从 52 涨到 61，两处文档没跟
- `check-claims.mjs` 自己有两处问题：一个从未被引用的 `claims` 数组（死代码，和刚删的 `label` 同类），扫描范围不含 `case/*.md`

**「改完」和「改上」是两件事。** commit message 说改了不算，得看 `git show` 里有没有那行。

## 案例代码自己查一遍

第四轮之后我意识到：前四轮主要在看文档和正文，**案例代码的功能从没被系统试过**。于是在浏览器里逐条验：

- 六种语法各试一遍 —— 这才发现 `quote` 从来没生效（见上）
- 边界：不闭合的标记、`<script>`、`<img/src=x/onerror=...>`、`#<svg/onload=...>`
- 脏数据：往 localStorage 里塞一个非 JSON，看会不会崩
- 组合：`**粗 \`码\` 粗**`、行首引用、行中 `>`、两行引用
- 五个版本的行为差异是否符合书里的说法

**顺带确认了书里最锋利的那条论据是真的**：往 v0.1 和 v0.2 各输入一次 `<script>alert(1)</script>`——

- v0.1 渲染成 `&lt;script&gt;`，页面里没有 script 元素
- v0.2 渲染出一个真的 `<script>` 元素

第 00 章说「重构弄丢了 HTML 转义」，实测站得住。

还发现四种新语法（删除线、链接、引用、列表）**没有样式**，用的是浏览器默认——链接是蓝色下划线，和整套设计语言不搭。补了样式。

## 加了什么工具

- `scripts/check-claims.mjs` —— 核对书里引用的所有行数。起因是**行数漂移了三次**（改代码之后书里没跟着改），而且不会有任何报错。
- `case/v1.1/store.test.ts` —— 起因是「测试在用」这句话当时是编的。补上之后就成真的了。
- `case/v0.4/verify.ts` —— 第 06 章声称「两版输出逐字节一致」，这个脚本跑 8 个样例 × 6 组开关来证。
